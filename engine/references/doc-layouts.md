# doc 形态的十二种版式

doc 形态的唯一手写源是期目录的 `doc.json`。一个场景就是一个对象，`type` 决定用哪种版式。

完整可跑的样例：`engines/doc/examples/doc-full-example.json`（后勤报修那期，10 场）。

---

## 每个场景都能用的通用字段

| 字段 | 类型 | 说明 |
|---|---|---|
| `say` | string | 这一场的旁白。**场景时长由它决定**：`max(minDur, delay + 配音时长 + hold)` |
| `delay` | number | 画面出来到开口的停顿，秒，默认 0.5。封面建议 1.5 |
| `hold` | number | 说完到切场的留白，秒，默认 1.0。金句页可以给 2.0 让观众看完 |
| `minDur` | number | 最短停留，秒。配音很短但画面信息多时用它撑住 |

> ⚠️ 配音停顿叫 `delay` / `hold`，**不叫 lead / tail**。`lead` 是版式的引导副标题，
> 两者曾经同名，JSON 里后写的会把先写的吃掉（画面直接显示成 `0.5`）。`wb doc check` 会拦住这种写法。

`say` 留空 = 这场不配音，只按 `minDur` 停。适合纯视觉的过渡页。

## 1. `cover` — 封面

```json
{
  "type": "cover",
  "kicker": "后勤保障数字化",
  "title": "后勤智能报修小程序",
  "sub": "拍照即报修　·　AI 自动分类派单　·　全流程可追溯",
  "meta": "微信小程序 ＋ 腾讯云开发　|　无需自建服务器",
  "say": "后勤智能报修小程序。拍张照片，系统自己找人。",
  "delay": 1.5, "hold": 0.6, "minDur": 4.6
}
```

- 深色铺满，左对齐。`title` 用 88px，**控制在 12 字以内**，超了会压到 `sub`
- `sub` 用 `·` 或全角空格分隔要点，别用逗号堆句子
- `brand.logo` 有值时会在标题上方显示
- `meta` 放技术栈 / 单位 / 日期，用 `　|　` 隔开

## 2. `cards` — 卡片网格

```json
{
  "type": "cards", "no": "01", "kicker": "现 状",
  "title": "现在是怎么报修的？",
  "lead": "电话、微信群、口头转达。楼栋和设施一多，四个问题会同时浮现。",
  "cols": 2,
  "items": [{"t": "描述不清，来回跑", "d": "一到场才发现带错工具，一次报修跑两三趟。"}],
  "footnote": "四个问题指向同一个原因。"
}
```

- `cols` 只能 2 或 3。**2 列放 4 张、3 列放 6 张**是最舒服的，再多会溢出一屏
- `item.d` 每张 2 行以内（2 列约 34 字、3 列约 28 字），超了卡片会被撑破
- `no` 会自动加铜棕竖条和 `01/02/03` 编号，不用自己写
- 入场节奏跟着场景时长自适应，配音长就慢点出，短就快点出

## 3. `turn` — 转折金句

```json
{"type": "turn", "old": "打电话找人", "new": "拍张照片提交", "note": "剩下的，系统自己判断该找谁"}
```

- `old` 会被强调色划掉（动画 26→56 帧），`new` 放大到 82px
- 全片最多用一次。用两次就不叫重音了
- `old` / `new` 各 4~8 字最好，长了会换行

## 4. `flow` — 流程时间轴

```json
{
  "type": "flow", "no": "02", "kicker": "方 案",
  "title": "报修人只做一件事：拍照提交",
  "lead": "分类、派单、通知、留痕，都由系统完成。",
  "steps": [
    {"no": "STEP 01", "t": "拍照提交", "d": "选楼栋、楼层与位置类型，拍 1 至 3 张现场照片。", "out": "工单 ＋ 现场照片"}
  ],
  "footnote": "每一步都有时间戳。"
}
```

- **最多 4 步**，超过会挤
- `out` 是"这一步产出了什么"，可选但强烈建议给 —— 它让流程有重量
- 未点亮的步骤以 13% 透明度做骨架占位，不会出现大片空白

## 5. `split` — 图文分屏

```json
{
  "type": "split", "no": "03", "kicker": "小程序端",
  "title": "打开，就只有一件事",
  "image": "assets/mp-index.png",
  "imageSide": "left", "imageW": 430,
  "imageRatio": 0.5925,
  "bullets": [{"b": "顶部只放身份与单位", "t": "，不堆功能按钮。"}],
  "chips": [{"label": "待受理", "tone": "amber"}, {"label": "处理中", "tone": "blue"}]
}
```

| 字段 | 说明 |
|---|---|
| `imageSide` | `left` / `right`。同一个片子连用两场时建议左右交替，形成镜像节奏 |
| `imageW` | 手机截图 400~440；界面截图 560~640 |
| `imageRatio` | 原始宽高比（宽/高）。`750×1266` → `0.5925`，`750×2240` → `0.3348` |
| `scroll` | `true` 时长图在容器里缓慢上滚。**必须配 `imageRatio`**，滚动量靠它算 |
| `bullets[].b` | 加粗前缀（结论），`t` 是后半句（解释）。这样读者扫一眼就能抓住重点 |
| `chips` | 状态色块，`tone` 取 `amber` / `blue` / `green` |

要点最多 4 条，多了会和图片抢高度。

## 6. `browser` — 浏览器窗口

```json
{
  "type": "browser", "no": "05", "kicker": "管理后台",
  "title": "浏览器打开，不用装客户端",
  "lead": "看全局、接工单、改配置、管人员 —— 四张表，全部可视化维护。",
  "url": "后勤报修 · 管理后台",
  "tabs": [{"img": "assets/admin-overview.png", "t": "概览", "d": "工单总量与状态分布、近 14 天趋势"}],
  "footnote": "改完立即生效。"
}
```

- 左边 1130×598 的窗口轮播，右边标签跟着高亮
- **2~5 张图**最合适。每张停留时间 = 场景时长 × 0.82 ÷ 张数，太多张就一闪而过
- 截图会被 `object-fit: cover` 裁掉底部约 15%，**重要内容放顶部**
- `tabs[].d` 一行说清这一页能干什么，30 字内

## 7. `ratio` — 数据比例条

```json
{
  "type": "ratio", "no": "06", "kicker": "AI 可靠性",
  "title": "AI 是预填建议，不是最终决定",
  "lead": "把 80% 的常见故障一次分对，剩下 20% 交给人。",
  "big": {"value": "80%", "label": "常见故障一次分对"},
  "small": {"value": "20%", "label": "转人工分派"},
  "rules": [{"t": "候选清单来自后台", "d": "模型只能在清单里选，编不出不存在的类别。"}],
  "stats": [{"n": "12", "u": "个", "l": "一级类别"}],
  "statsNote": "全部可在后台维护"
}
```

- 比例条长度按 `big.value` / (`big` + `small`) 自动算，写法带 `%` 或纯数字都行
- `rules` **最多 4 条**（2×2 网格），标题 ≤10 字，描述一行
- `stats` 是底部规模数字，可省略；给了就会占住底部
- 这场是深色铺满，全片的信息密度高点，建议放在片子中后段

## 8. `words` — 大词金句

```json
{
  "type": "words", "no": "07", "kicker": "预期效益",
  "items": [
    {"a": "一次", "b": "分对", "d": "常见故障直接落到责任部门", "s": "省掉转达与二次确认"}
  ],
  "footnote": {"t": "更重要的是，留下一份过去没有的数据", "d": "哪栋楼报修最频繁……"}
}
```

- `a` 用主色、`b` 用强调色，拼起来是一个词（"一次"+"分对"）
- **2~4 组**。字号按最长那组的字数自动收，不会换行
- `s` 是小字补充，可省略
- `footnote` 是底部整行说明，可省略

## 9. `terminal` — 终端窗口

```json
{
  "type": "terminal", "no": "02", "kicker": "方 案",
  "title": "剩下的，系统自己跑完",
  "lead": "报修人提交之后，这几件事在后台自动完成。",
  "cmd": "repair dispatch",
  "lines": [
    {"t": "识别故障类别与置信度", "s": "AI"},
    {"t": "生成工单号并开始计时", "s": "完成"}
  ],
  "foot": "全程无需人工分派"
}
```

- 深色窗口，圆点标题栏，逐行执行；**最后一行转强调色**表示"当前正在做"
- `cmd` 是窗口标题栏里那行命令名，可省
- `lines[].s` 是右对齐的状态标签（AI / 规则 / 完成），可省
- `foot` 是窗口底部带光点的状态行，可省
- **≤6 行**，7 行起会顶出画面
- 适合：自动化流程、后台任务、安装步骤、批处理

## 10. `cmdlist` — 命令行清单

```json
{
  "type": "cmdlist",
  "label": "常见故障对照表",
  "rows": [
    {"cmd": "灯不亮 / 闪烁", "desc": "照明线路 → 电工班"},
    {"cmd": "空调不制冷", "desc": "暖通设备 → 空调班"}
  ],
  "foot": "清单在后台维护，改完立即生效"
}
```

- 左命令右说明，**念到哪一行哪一行亮**，其余压暗
- 高亮行带强调色竖条 + 命令变强调色
- **≤5 行**，再多行高不够、压暗行会看不清
- 适合：命令速查、对照表、操作步骤、参数说明

## 11. `ring` — 环形数据

```json
{
  "type": "ring", "no": "06", "kicker": "AI 可靠性",
  "title": "八成常见故障，一次分对",
  "lead": "剩下两成转人工，不硬猜。",
  "value": "80", "unit": "%", "sub": "一次分对",
  "progress": 0.8
}
```

- 左边一个环 + 中心大数字，右边标签、标题、引导句
- `progress` 是 0~1 的填充比例，`value` 是环里的字（可以跟 progress 不一致，比如环画 0.8、写 "80%"）
- 适合：达标率、覆盖率、占比、单个关键指标

## 12. `end` — 收尾

```json
{
  "type": "end",
  "title": "后勤智能报修小程序",
  "sub": "微信小程序 ＋ 腾讯云开发",
  "tagline": "拍照即报修　·　AI 自动分类派单　·　全流程可追溯",
  "credit": "音乐 reCreation · airtone · CC BY 3.0"
}
```

- `credit` 是 BGM 署名，用了 CC BY 的音乐就必须留（白板那边的 `assets/bgm.mp3` 如果是 CC0 可以不给）
- 最后 20 帧整体淡出，不用自己加

## 图片规格

放期目录的 `assets/`，`doc.json` 里写 `assets/xxx.png`（相对期目录）。

- **优先 2 倍图**（2880×1800 的界面、750×1266 的手机）。1920 画布上会缩着用，细节不糊
- 手机截图给完整屏内容（不要带手机外壳），版式里已经有圆角和投影
- 界面截图给完整窗口（不要带浏览器边框），`browser` 版式自己画边框

## 怎么排一场的顺序

一般套路（后勤报修那期就是这个结构，10 场约 95 秒）：

```
cover → cards(问题) → turn(转折) → flow(方案) → split(界面) → split(界面) → browser(后台) → ratio(可信度) → words(效益) → end
```

不是每期都要全用。三步方案 4~6 场就够：

- **产品介绍**：cover → cards(痛点) → split(界面) → split(界面) → words(价值) → end
- **方案汇报**：cover → cards(现状) → flow(方案) → ratio(指标) → words(效益) → end
- **数据报告**：cover → ratio(核心指标) → cards(拆解) → browser(明细) → words(结论) → end
